# Product + device onboarding (HTTPS) → first-packet toast → configuration → history

**Written:** 2026-09-22 · **By:** frontend · **Verification:** live-tested end to end, with the real
seeded user (`junead@chaminade-hs.org`) and a real webhook `POST` to `http://localhost:8080/api/webhook`
— not a demo-mode simulation.
**Source:** `src/forms/MultiStepForm/{AddDevices,SecondstepForm,ThirdstepForm,FourthstepForm}.tsx`,
`src/screens/{ManageProduct,ProductConfiguration,ManageDevice}.tsx`,
`src/components/{HTTPProtocol,GlobalPacketListener}.tsx`, `src/utils/packetToastManager.tsx`.

**Prerequisite:** user is logged in (real account; register or Google login both land here eventually).

**Steps:**

Shows every packet received for this product after configuration.                                                                                                                                                                                                                   |

**Realtime events involved:** `packet:initial` only (step 9). `dashboard:update`/`building:update` are a
separate flow (dashboard widgets / asset tree), not part of onboarding.

**Model:** one product → many devices → one shared webhook token → one shared attribute/alert config.
A different device category or a different alerting ruleset means a **new** product (and its own token),
not a second device type bolted onto an existing product.

**Known gaps / open questions:** see `../findings.md` for the live-tracked list — as of this writing:
`POST /highlight-attributes` 404s; onboarding UI's displayed webhook URL is hardcoded to prod; MQTT
connectivity is UI-present but not functional end-to-end (both sides, known, not being worked now).
