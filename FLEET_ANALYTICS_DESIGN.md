## 0. UI QUALITY BAR — NON-NEGOTIABLE (owner, 2026-09-25 ~07:57 PKT: "we can't compromise on UI, I want the best and most beautiful enterprise-grade UI")

This overrides speed: a screen is **not done** until it meets this bar. The owner's own words are the acceptance test — if it does not look like a best-in-class enterprise product, it is not finished.

**Look & feel**

- **Reference level:** the polish of Linear / Stripe Dashboard / Datadog / Vercel / Samsara — calm, dense-but-airy, precise. No "developer default" look: no unstyled tables, no raw HTML controls, no placeholder text, no lorem, no janky charts.
- **Visual hierarchy first:** one clear primary focus per screen, generous whitespace on an 4 / 8 px spacing scale, consistent radii and borders, a real type scale (display numbers in the display font with tabular figures, labels in small caps-tracking style already used by the app), aligned grids at every width.
- **Design tokens only:** colours, spacing, radii, shadows, motion durations come from tokens (`--color-*`, existing Tailwind tokens); no hard-coded hex in components (chart palettes are token-derived). Dark and light are designed, not inverted — both screenshot-reviewed for every screen.
- **Charts are crafted:** smooth curves / rounded columns, subtle gradient fills, soft grid, tabular-figure axes, rich tooltips with delta and definition, legends that are also filters, animated entrance (≤ 300 ms, respects `prefers-reduced-motion`), crosshair on time series, target lines, sparkline-in-table, direct value labels on ranked bars, sensible empty / single-point / huge-number states.
- **Motion with purpose:** skeleton shimmer that matches the final layout (no layout shift), number count-up on first load only, hover / focus feedback on every interactive element, smooth panel transitions; never decorative noise.
- **Every state is designed:** loading (skeleton), empty (illustration-free but helpful, with the next action), error (retry + reason), partial data ("telemetry on 2 of 66 vehicles"), stale data ("updated 2 min ago"), permission-denied.
- **Typography & numbers:** locale-aware formatting, compact units (12.4 k, 3.2 M), units always shown, currency from the company setting, dates in the company timezone, no truncated important text (tooltips for the rest).
- **Density modes** (comfortable / compact) for tables; sticky headers, column chooser, row hover, keyboard navigation.
- **Accessibility as polish:** WCAG AA contrast on both themes, visible focus rings, meaning never by colour alone, full keyboard operation, ARIA on charts (summary + data table alternative), reduced-motion support.
- **Responsive:** desktop-first enterprise layouts verified at 1280 / 1600 / 1920 px wide **and** tablet width; no horizontal page scroll; wide screens use the space (more columns, not stretched cards).
- **Consistency across the whole Fleet module:** the same components (from the widget kit) everywhere — a KPI tile is the same on Overview and Analytics; the existing Fleet screens are brought up to this bar over time (skeletons, empty states, chart palette, spacing).

**Process (how the bar is enforced)**

1. **Before building charts, load the `dataviz` skill** (palette / mark specs / interaction rules, validated colour formula) and use its palette validator for every categorical / sequential / diverging palette; for any standalone HTML page use `artifact-design`.
2. **Design first, then code:** for each new screen produce a quick visual mock (in the app on mock data, or an HTML artifact) and show the owner before wiring real data when the layout is new.
3. **Every screen is screenshot-reviewed** in dark **and** light, at ≥ 1600 px wide (resize the browser window; the MCP window default of ~1250 px hides layout problems), with real-looking data (seeded ZZ data at scale) and with empty / loading / error states forced; fix everything that looks off before saying "done".
4. **Checklist before any UI is called done:** hierarchy clear · spacing on scale · tokens only · both themes · 3 widths · all states · hover / focus / keyboard · numbers formatted + units · tooltips + definitions · no layout shift · no console errors · matches the widget kit.
5. **Say plainly what was NOT visually verified**; unverified = TODO in `task.md`, never "done".

## 1. Principles

1. **Answer decisions, not "show data".** Every widget exists because someone acts on it: dispatch, maintenance, compliance, safety, finance. Each widget therefore has an owner question, a click-through, and a definition.
2. **Numbers must reconcile.** One definition per metric, one source per number, shown in a glossary tooltip ("ⓘ How is this calculated?"). The same figure never appears on two widgets with different values.
3. **IoT-derived where a tracker exists, honestly labelled where not.** Utilisation / idle / distance come from telemetry; vehicles without a tracker fall back to trip records and are flagged ("trip-based"). Coverage is shown (e.g. "Telemetry on 2 of 66 vehicles").
4. **Live above, historical below.** _Overview_ = what is happening / needs attention now (realtime). _Analytics_ = how are we doing over a period (filters, comparison, drill-down, export).
5. **Scale first.** Server-side aggregation, paged tables, top-N + "view all", no unbounded lists (the current 66-row table breaks at thousands).
6. **Every widget is clickable** (opens the filtered list / report / vehicle / driver / trip), has loading skeleton, empty state with next step, "as of" time, and works in light + dark.

## 2. Information architecture — FINAL DECISION (2026-09-25 ~07:55 PKT)

**Separate pages, grouped under the one existing sidebar entry "Fleet Management", in three areas, each deep-linkable (real URLs):**

| Area           | Route                            | Pages                                                                                                                                        | Audience / nature                                                                            |
| -------------- | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| **Operations** | `/fleet-management/operations/…` | **Overview** (the dashboard, landing page) · Map · Trips · Vehicles · Drivers · Assignments · Yards · Geofences · Incidents                  | dispatch / ops — live, transactional (today's tabs, re-homed; Overview replaces "Dashboard") |
| **Analytics**  | `/fleet-management/analytics/…`  | Utilisation · Trips & delivery · Fuel & efficiency · Maintenance & compliance · Drivers & safety · Costs · (later) Saved & scheduled reports | managers — historical, filterable, comparable, exportable                                    |
| **Ledger**     | `/fleet-management/ledger/…`     | Entries (table + forms) · Profit & loss · Receivables · (later) Budgets                                                                      | finance — records you create and edit; will get its own permission                           |

- **Analytics and Reports are ONE area:** every analytics page _is_ a report (summary tiles + charts + a paged table + Export CSV/PDF + Save view + Schedule). A separate "Reports" area would duplicate filters and tables; the only extra page is the later "Saved & scheduled reports" library.
- **Why not one page for everything:** too heavy to load and too long to read, cannot be deep-linked or bookmarked per report, cannot be permissioned (ledger vs operations), and mixes live and historical views with different refresh rules.
- **Why not four unrelated sidebar entries:** they share one filter bar, one widget kit and constant drill-downs (a cost bar → the ledger entries behind it; a KPI → its report); keeping them under Fleet Management keeps that navigation short.
- **Navigation UI:** the current 9-tab bar becomes a two-level nav — three segment buttons (Operations · Analytics · Ledger) and, under the active one, its page tabs. Tab state moves into the URL (Next optional catch-all `app/(app)/fleet-management/[[...slug]]/page.tsx`; old `/fleet-management` redirects to `/operations/overview`). Deep links from dashboard widgets, alerts and emails work.
- **Global filter bar** (Overview + every Analytics page, synced to the URL query string): date range (Today / 7D / 30D / MTD / Custom) · compare toggle (vs previous period / same period last year) · scope (vehicle category, vehicle, driver, customer, cost centre) · company timezone shown. Filters carry over when moving between Analytics pages; the last used range is remembered per user.

### 3.1 KPI tiles (six) — form: number + delta chip + 14-day sparkline; whole tile clickable

| KPI                    | Definition (proposed)                                                                                                            | Click →                    | Good / bad direction         |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------- | ---------------------------- |
| **Fleet availability** | in-service vehicles not in maintenance ÷ all `active`+`in_maintenance` vehicles                                                  | Vehicles filtered          | higher = good                |
| **Utilisation**        | moving hours ÷ available hours (available = in-service vehicles × scheduled hours); telemetry-based, trip-based fallback flagged | Analytics → Utilisation    | higher = good (target-aware) |
| **On-time delivery**   | completed trips arriving ≤ planned end + grace ÷ completed trips that had a plan                                                 | Analytics → Trips          | higher = good                |
| **Cost per km**        | (fuel + maintenance + other ledger costs) ÷ km driven                                                                            | Analytics → Costs          | lower = good                 |
| **Fuel economy**       | Σ km ÷ Σ litres (full-tank method)                                                                                               | Analytics → Fuel           | higher = good                |
| **Open issues**        | overdue maintenance + expired documents/licences + critical alarms + severe incidents (7 d)                                      | scrolls to Needs attention | lower = good                 |

Delta chip: ▲/▼ + %, **colour by polarity** (good = green, bad = red, |Δ| < 2 % = neutral grey), never colour-only (arrow + text).

| Widget                       | Form (why this one)                                                                                                                                                                                                                                                                                                                                         | Encoding / colour                                                                                                              |

Colour rules: semantic (status/severity) colours are **fixed and reused everywhere**; categorical chart colours come from one accessible palette (colour-blind safe, ≥ 3:1 contrast on both themes, defined as tokens); never encode meaning by colour alone (icon/label/pattern too); deltas by polarity; red is reserved for "bad / act now".

## 4. Analytics area (historical, one page per decision)

Common layout: filter bar → **summary tiles with deltas** → primary chart → secondary chart(s) → **paged, sortable, searchable table** (server-side) → **Export CSV / PDF**, "Save view", "Schedule email" (later). Every table row drills into the vehicle / driver / trip.

| Page                         | Owner question                                 | Charts (form)                                                                                                                                                                                                                           | Table                                                                                     |
| ---------------------------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| **Utilisation**              | Are vehicles earning their keep?               | Utilisation trend (**line/area**, target line) · Moving vs idle vs parked hours (**stacked column**) · **Heatmap** day-of-week × hour (when do we drive) · Distance per day (**column**)                                                | Per vehicle: km, moving h, idle %, utilisation %, trend sparkline                         |
| **Trips & delivery**         | Are we on time, and why not?                   | Trips by status (**stacked column**) · On-time % trend (**line** + target) · Trip duration **distribution** (histogram) · Cancellation reasons (**horizontal bars**) · Planned vs actual distance (**scatter/variance bars**)           | Trips with delay, distance variance, customer                                             |
| **Fuel & efficiency**        | Are we wasting fuel?                           | Fuel economy trend (**line**) · Litres & cost per period (**column + line**) · Price per litre (**line**) · Efficiency by vehicle category (**bars**) · Anomalies (fills > tank, economy drop) as a **flag list**                       | Fills: vehicle, station, litres, cost, economy, anomaly flag                              |
| **Maintenance & compliance** | Will anything stop us from running?            | Due/overdue buckets (**stacked bars**) · Maintenance cost per period (**column**) · Downtime days (**column**) · Compliance rate (**gauge/bullet**)                                                                                     | Schedules with next-due date/km, status; documents & licences with expiry                 |
| **Drivers & safety**         | Who is safe and productive?                    | Driver scorecard (**ranked bars + sparklines**) · Incidents by type/severity (**stacked**) · Incidents per 100 000 km (**line**) · Licence status (**donut**)                                                                           | Per driver: trips, km, on-time %, incidents, idle %, harsh events (when telemetry exists) |
| **Costs** (→ Ledger)         | Where does the money go, and is it profitable? | Cost by category (**donut**) · Cost trend (**stacked column**) · Cost per km & per vehicle (**bars**) · Revenue vs cost vs profit (**combo**, once billing feeds it) · Receivables ageing (**stacked bars 0–30 / 31–60 / 61–90 / 90+**) | Ledger entries (paged, filterable, exportable)                                            |

Deliberately **not** used: 3-D, pies with > 6 slices, **any dual-axis chart**, radar charts, gauges for anything that is not a target.

## 5. Metric glossary (definitions to agree with backend — see flow 07 A1–A6)

Distance: telemetry (GPS odometer) → vehicle odometer delta → trip actual distance, in that order, one number everywhere. Fuel: fuel logs, economy by **full-tank method**. Trip belongs to the period of `actual_start_at`, else `planned_start_at` (fixes the "2 trips instead of 24" bug). Status freshness threshold: one company setting (default 15 min), used by the map and the dashboard. "No tracker" ≠ "Offline". Days bucket in the **company timezone**. Utilisation available hours exclude retired/sold and (optionally) maintenance downtime.
