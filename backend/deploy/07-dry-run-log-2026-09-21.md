# 07 — Dry-run log (2026-09-21) and lessons learned

Before writing these notes the production Docker stack was run end to end on the development laptop (after stopping the pm2 processes), and the
integrations (Google login, Gmail SMTP, Cloudflare R2) were brought up one by one in the days before. This is the honest list of what went wrong or
surprised us, what we changed, and what you still have to remember. Every item below is already reflected in the templates/docs; this page explains _why_.

## Issues found and what we did about them

### 1. `.env.production` (copied from an old template) was not deployable as-is

- **No `POSTGRES_PASSWORD`** — required by `docker-compose.prod.yml` (it refuses to start, with a clear message). → added to `.env.example` with a comment.
- **Placeholder secrets** (`change-me-dev-only`) in five variables. → generate real ones ([02 §1](02-environment-variables.md)).
- **`JWT_ACCESS_TTL=900`** was set explicitly, silently overriding the decided 7-day login token (D-0125). → template now says `604800`.
- **`LOG_LEVEL=debug` / `NODE_ENV=development`** in the template. → template comments say `info` / `production` on a server.
- **A leftover `ORACLE_MYSQL_URL`** (the temporary legacy database used during the rewrite; not read by the app). → removed from the template; never deploy it.
- **`DATABASE_URL`/`REDIS_URL` pointing at `localhost:5442/6389`** (the laptop's dev containers). Harmless for Docker — compose overrides both for every service — but confusing; on the pm2 path they must be real.
- **`MQTT_URL=mqtts://your-hivemq-host:8883`** placeholder would make the MQTT process reconnect to a fake host forever. → leave it empty when there is no broker.

### 2. The bootstrap creates a publicly known admin account

The first-run seed always created `junead@chaminade-hs.org` / `password123` (admin of a "Default Company") — Laravel's own seed user. Fine on a laptop, a
backdoor on a real server. → new switch **`SEED_DEMO_USER=false`** (D-0134) skips only that user; the real catalogs the app needs are still seeded.
Verified on a throw-away database: only `superadmin@example.com` exists afterwards, protocols (2 since D-0135; 6 at the time) and modules (8) are present.

### 3. The super-admin password appears only in the `migrate` container's log

Generated once, printed once. `docker compose … logs migrate | grep "Generated password"` right after the first start; store it immediately ([04](04-path-a-docker.md)).

### 4. Port clash with pm2 on the laptop

Both the dev pm2 processes and the compose `http` service use 8080. → `npx pm2 stop …` first (not `delete`, so they can be restarted afterwards). On a server this doesn't arise.

### 5. The Docker database is fresh

The compose stack has its own volume — none of the pm2 development data (products, devices, test users) is in it. Register or use the seeded users to test.

## Integration lessons from the days before (they explain several defaults)

### Google sign-in kept ending on `login?error=auth_failed` — Node's 250 ms connect timeout (D-0133)

The consent screen worked, the callback arrived with a valid code, but the server's call to `oauth2.googleapis.com` failed with `ETIMEDOUT` after 284 ms while `curl` to the same host
worked. Node's "happy eyeballs" gives each address only **250 ms** to connect; on a link where the TCP connect takes 0.5–2 s (and IPv6 has no route) every attempt times out.
→ every process now sets a 5 s per-attempt timeout (`NETWORK_CONNECT_ATTEMPT_TIMEOUT_MS`, `src/platform/network/tuning.ts`); the failure is also logged now (`Social login callback failed`).
A well-connected server won't notice, but the setting costs nothing there.

### Registration e-mails weren't arriving — SMTP was simply not configured (D-0131)

Node's `.env` had no `SMTP_*`; the mailer then only _logs_ the e-mail (`SMTP not configured — logging email instead of sending`). Fixed with Laravel's effective SMTP settings; the e-mail body was
also ported to Laravel's branded template. Side effect worth remembering: **once real credentials are in `.env`, the test suite would try to use them** — `vitest.config.ts` now blanks
`SMTP_*`, `R2_*` and `GOOGLE_*` for every test run.

### R2 uploads were refused — the API token was "Object Read only" (403 on PUT/DELETE, but listing and reading worked)

Recreate the token with **Object Read & Write** scoped to the bucket. A quick way to tell: list works, put/delete return `AccessDenied` ([03](03-external-services.md)).

### The Google client in Laravel's `.env` was the previous developer's

You can't add redirect URIs to a client you don't own → create your own OAuth client ([03](03-external-services.md)). The redirect URI is per _backend_ address (`…/api/auth/google/callback`), not per frontend.

### A frontend login page depends on the API origin

The frontend's Google popup only trusts a message whose origin equals its configured backend origin; the popup page posts to `FRONTEND_URL`. Both must be updated when the API moves.

### Tokens expire in 7 days now

Not a deployment step, but useful: login tokens (`token`/`access_token`) last 7 days like Laravel's. The proper two-token design (short access token + httpOnly refresh cookie) is deferred (`migration/KNOWN_ISSUES.md` 11.64).

## Known gaps (not deployment blockers)

- The compose Redis has no persistence — queued jobs vanish on a Redis restart.
- The OpenAPI contract file (`migration/reference/openapi.yaml`) is stale relative to the Phase 7 fixes and its drift-check script was never written (`KNOWN_ISSUES` 11.65) — required before handing the contract to the frontend team.
- Google profile pictures are not imported on first Google sign-in (Laravel didn't either).
- Cloudflare R2 `r2.dev` public URL is for testing; attach a custom domain for production.
